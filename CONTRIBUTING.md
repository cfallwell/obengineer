# Contributing

This directory holds the instrumentation architecture agentry: agent definitions,
the three-run prompt workflow, canonical skills, and the plugin bundle that
distributes them to Cursor, Codex, and Claude Code. Customer deliverables live under
`../docs/observability/`.

## Setup

```bash
make deps          # python-docx and pytest — the only dependencies
make test          # contract tests + renderer round-trip
make check         # plugin sync and manifest agreement
```

## Where to make a change

| Changing | Edit | Then |
|---|---|---|
| What an agent must always produce | `agents/*.agent.md` | Add or update the matching row in the completeness bar, and a test in `tests/` if it is a hard requirement |
| The customer document's shape | `skills/references/document-template.md` | Re-render an existing deliverable and run `verify_render.py` to prove the template still renders |
| The baggage contract | `skills/references/cross-cutting-attributes.md` | Confirm `tests/test_skill_contracts.py` still passes; it asserts the five code subsections exist |
| A skill's behaviour | `skills/<skill>/` | `make sync-plugin-skills`, then commit both the canonical file and the plugin copy |
| The renderer | `skills/customer-doc-render/scripts/` | Add a test that fails without the change |
| A copy-paste prompt | `prompts/` | Keep it consistent with the agent it names |

**Never edit `plugins/obengineer/skills/**` or the companion `agents/` and
`prompts/` copies inside the plugin.** They are generated by
`scripts/sync_plugin_skills.py`; the next sync reverts a hand edit silently.

## Adding a skill

1. `skills/<name>/SKILL.md` with YAML frontmatter: `name` matching the directory,
   a `description` that names its `$<name>` invocation and the phrases a user would
   actually type, and `metadata` with author, version, and category. Keep the
   description under 1,536 characters — hosts truncate longer text and the skill
   stops being discoverable.
2. Progressive disclosure: put depth in `references/`, executables in `scripts/`,
   tests in `tests/`. `SKILL.md` states the process and links to the rest rather than
   inlining everything.
3. Add the skill to the tables in `README.md` and `AGENTS.md`.
4. `make sync-plugin-skills && make test`.

Shared content that more than one skill needs goes in `skills/references/`, not
duplicated into each skill.

## Writing style for skills and agents

- **No invented taxonomy.** Never name a customer's journeys, business transactions, metric names, or industry. Examples are generic (`<org>`, `<app>`, `<bus>`) or explicitly labelled as examples of shape.
- **State the reason, not just the rule.** "Use an allowlist" is a rule someone will work around; "a loop over every baggage entry stamps whatever a future caller put there, which is how tokens reach production" is a reason they will not.
- **Prefer the failure mode.** The most useful line in a skill is usually the one describing what breaks when the step is skipped.
- **No credential values.** Tokens are `window.__<ORG>_RUM_TOKEN__`, `${ENV_VAR}`, or a named secret store — including in `.mcp.json`. The credential scan in `tests/` fails the build otherwise, and it will catch a vendor's documentation example key too.

## Pull requests

- One logical change per commit; one concern per PR.
- `make test` and `make check` pass.
- If a skill changed, the sync ran and its output is committed.
- If the document template changed, a re-render is attached or described.
- No customer PII, credentials, or scan artifacts containing either.

## Tests are a record of real defects

`skills/customer-doc-render/tests/` encodes bugs that shipped: bold wrapping a code
span printing literal backticks, ordered lists counting continuously across the whole
document, blank lines inside code blocks growing taller than the code, headings
miscounted because a `#` comment sat inside a fence, and bold spans wrapping across
source lines. Do not delete one of those tests to make a change pass — the defect it
describes will come back.
